# 内容管理：块编辑器和 AI 对话（设计 v1）

2026-11-22 定。接着开发方案 5.6（内容管理，C0–C3 已完成）。改动 5.6 的两条：第 7 条"正文用 Markdown 编辑"改为块编辑器；"内容管理模式没有 AI 对话""读写结果不交给 AI"改为下面第二部分的规则。实施后把结论并回开发方案 5.6，分层写进第 14 节。

## 已定的问题（2026-11-22，用户逐项选定）

1. **顺序**：先做块编辑器（E 层），再做 AI 对话（A 层）。正文怎么表示由编辑器决定，AI 改正文时用同一种表示，先定下来，AI 那边少返工。
2. **编辑器**：Notion 式块编辑器（所见即所得、`/` 菜单、拖动块），用 BlockNote。
3. **AI 写入**：AI 只提出修改，界面列出要改的属性和正文差异，用户确认后才写进 Notion。和网站改动要审核的规则一致。
4. **AI 范围**：可以修改当前条目，可以在当前数据库里新建条目。不能批量改别的条目，不能删除，也不能跨数据库。

## 第一部分：块编辑器（E 层）

### 核实结果（2026-11-22）

- BlockNote 0.57.0（2026-10-30）：`@blocknote/core`、`@blocknote/react`、`@blocknote/shadcn` 都是 MPL-2.0。React 的要求是 `^18 || ^19`，项目用 19.3.1；`@blocknote/shadcn` 要求 Tailwind `^4.1.12`，项目用 4.3.5，和现有的 shadcn 组件一致，不需要 Mantine。
- 语言包有 `zh`、`en`，没有马来文。
- 多人协作依赖（yjs 等）是 peer 依赖，不用协作就不装。

### 要定的问题（按建议定下，开工前可以再改）

1. **正文的表示改成块结构**：接口里的正文从 Markdown 改成共享类型 `ContentBlock[]`，只描述支持范围内的块：段落、标题 1–3、无序和有序列表、待办、引用、代码（带语言）、分隔线、图片（外链，或保留原样的 Notion 托管图片），富文本是带粗体、斜体、删除线、行内代码、链接的文字段。
   - 服务端负责 Notion 块和 `ContentBlock` 互转，保存前仍按支持范围检查、仍做冲突检查，规则和 5.6 一样；zod 校验请求体，长度按 Notion 的限制。
   - 浏览器负责 `ContentBlock` 和 BlockNote 块互转。服务端不认识 BlockNote，以后换编辑器不用改接口。
   - 不在浏览器里解析 Markdown：否则要在前端再写一遍现在服务端的 Markdown 方言。
   - 现有的 Markdown 方言（`notion-blocks.ts` 的读写）留给 A 层：AI 读写正文时用 Markdown 比用 JSON 可靠。A 层如果改用块结构，再删掉 Markdown 方言。
2. **能编辑的范围先不变**：和 5.6 第 7 条一样，有表格、折叠、颜色、嵌套段落等内容时仍然只读。BlockNote 的块类型和样式按这个范围裁剪：去掉表格、折叠、文件、视频、音频、下划线、文字颜色、背景色、对齐。嵌套只允许列表里套列表，保存前在浏览器里先检查并说明，服务端再检查一次。扩大范围（表格、折叠、颜色）以后另定。
3. **图片**：只能填外链，不提供上传。Notion 托管的图片显示出来、可以移动或删除，不能换地址；保存时原样保留这个块（和现在一样）。
4. **语言**：界面是中文时用 BlockNote 的 `zh`，英文用 `en`，马来文先用 `en`（BlockNote 没有马来文），是已知取舍。
5. **依赖**：`@blocknote/core`、`@blocknote/react`、`@blocknote/shadcn` 都用精确版本 0.57.0。编辑器所在的组件按需加载，打开正文时才下载，不影响其他页面的首屏。
6. **其他不变**：草稿（`draft.ts`）改为保存块结构；保存、冲突提示、"保存后不能撤销"的说明、只读时"在 Notion 中打开"都不变。

- **E2 收尾**：去掉 Markdown 提示文字，更新 README、开发方案 5.6、用户使用说明里内容管理相关的段落，三种浏览器跑完整 e2e。

### E0、E1 实现说明（2026-11-22）

- **共享类型**（`shared/src/content.ts`）：`ContentSpan`、`ContentBlock`（列表项最多带一层列表子项；`notion_image` 带 id 和只用于显示的签名地址）、`contentLength`、`CONTENT_BLOCKS_MAX`、`CONTENT_CODE_LANGUAGES`（从服务端移过来，编辑器的代码语言用同一张表）。请求体 `ContentBodyUpdate`、`ContentPageCreate` 改为 `blocks`，最多 5000 个顶层块、正文文字和地址合计不超过 `CONTENT_BODY_MAX`。
- **服务端**（`notion-blocks.ts`）：`readBody` 读成块结构，有问题时块为空、`unsupported` 写原因；不能按批次写回的正文记 `unwritable`。`contentToItems` 把块转成要写的 Notion 块，代码语言、图片地址和子项数量不合规时拒绝。Markdown 方言保留给 A 层。保存后返回的正文给保留下来的 Notion 图片补上原来的签名地址。
- **浏览器**（`features/content/blocks.ts`）：`ContentBlock` 和 BlockNote 文档互转。不能保存的情况在浏览器里先说明，保存按钮不可用：`nesting`（非列表项有子项，或子项不是列表项、有第二层）、`image_copy`（复制了 Notion 托管图片，签名地址一小时后失效）、`link`（链接不是 http、https、mailto）、`unsupported`。没有地址的图片不保存；Notion 图片地址没变就保持 `notion_image`，换了地址就成为外链图片；说明文字没改时保留原来的样式。末尾的空段落不保存（编辑器总留一个），比较草稿时也忽略 Notion 图片的签名地址。
- **编辑器**（`BodyEditor.tsx`，按需加载）：块只有段落、标题 1–3、三种列表、引用、代码、分隔线、图片；样式只有粗体、斜体、删除线、行内代码。工具栏只有块类型、图片说明/替换/删除、四种样式和链接；拖动手柄菜单只有删除；斜杠菜单去掉表情。深色模式跟随界面（`useDark` 移到 `lib/theme.ts`）。
- **列（`PageEditor.tsx`）**：编辑器只在加载时读一次正文。重新读到的正文（保存、重新载入）和编辑器里的不一样、而且没有草稿时才重新装载，保存后内容一致就不打断编辑。回到有草稿的条目时从草稿装载，并补上 Notion 图片的签名地址。保存时编辑器只读。
- **CSP**：管理界面的 `img-src` 加 `http:` 和 `https:`（外链图片可以是这两种，见下面评审意见），用来显示外链图片和 Notion 的签名图片地址；打开正文时图片所在的网站能看到请求（不带 referrer），是已知取舍。tiptap 的基础样式用页面的 nonce 注入（`injectNonce`）。BlockNote 和 base-ui 初次渲染时有几处 `style` 属性被 CSP 报告，元素最终的样式由 React 设置、布局正确，控制台会有这些报告。
- **已知取舍**：换行（`\n`）跟在粗体字后面时会带上粗体，Notion 里显示一样；正文编辑器的语言在打开时定下，切换界面语言后重新打开条目才变。编辑器的代码块约 1 MB（gzip 约 325 KB），只在打开正文时下载。
- **测试**：服务端每种块的往返、只读原因、拒绝不合规的块；浏览器 `blocks.test.ts` 覆盖往返、Notion 图片、嵌套和链接检查、末尾空段落；`draft.test.ts` 改成块结构并覆盖不能保存的状态；`e2e/content.spec.ts` 在编辑器里输入 `- ` 开始列表、保存、新建，三种浏览器通过。

## 第二部分：AI 对话（A 层）

### 已定的问题（2026-11-22，用户逐项选定）

1. **位置**：中栏底部的可折叠面板。条目列表和条目页都能用：在列表里可以让 AI 新建条目，打开条目时 AI 看得到当前条目。不占右栏的属性。
2. **对话记录按数据库保存**：每个数据库（数据源 + 数据库）可以有多段对话，接着聊或新开；每条消息带上当前打开的条目，AI 知道用户在看哪条。会话记录和网站的一样存在加密数据库里。
3. **AI 能读**：当前条目的属性和正文、数据库的字段和选项、搜索和读取同一个数据库里的其他条目。
4. **AI 能写**：只能修改当前打开的条目、新建条目，每次都先生成确认卡，用户确认后才写进 Notion（第一部分已定）。
5. **模型**：沿用网站构建的模型设置。

### 按建议定下的细节（开工前可以再改）

- **5.6 规则的变化**：5.6 原来写明"读写结果不交给 AI"。改为：只有用户在内容管理的对话里发消息时，AI 才通过工具读条目，读到的内容进入对话、会话记录，并发给模型服务商；不发消息就不读。Notion token 仍然不交给 AI，工具在服务端用数据源的 token 调 Notion，接口仍在 PIN 锁之后。面板里写明"对话内容会发给模型服务商"。
- **只有内容工具**：这类会话没有文件工具、网站锁、改动集和 Bukit；Pi 只拿到下面的自定义工具，工作目录是应用数据目录下的空目录。不影响网站和主题的会话。
- **工具**：
  - `read_entry`（当前条目或指定 id，同一数据库内）：属性和正文，正文用现有的 Markdown 方言（AI 读写 Markdown 比 JSON 可靠）；正文只读的条目返回原因。
  - `read_schema`：字段、类型、是否可编辑、单选/多选/状态的选项。
  - `search_entries`：按标题搜索、排序、翻页，返回标题和常用属性（和条目列表一样）。
  - `propose_update`：当前条目的属性变化和/或新正文（Markdown）。不是当前条目、条目正文只读、属性不可编辑或值不合规时直接返回错误让 AI 改。
  - `propose_create`：新条目的属性和正文。
  - 每次调用 `propose_*` 记下一份提议（存在会话记录的工具结果里，刷新后还在），返回"等待用户确认"，AI 这一轮不再继续写。
- **确认卡**：对话里每份提议一张卡，列出属性的旧值和新值、正文的差异（按行），按钮"写入 Notion"和"不要"。写入走现有的保存接口和冲突检查：提议记下读取时的编辑时间，写入前 Notion 里被改过就 409，卡上提示重新让 AI 读取。写入结果（成功、失败、拒绝）作为下一条消息的上下文告诉 AI。写入成功后刷新条目列表和打开的条目；条目页有未保存的草稿时，修改当前条目的卡不能写入，先保存或放弃草稿。
- **一次多张**：AI 可以一次提出多份提议（例如批量新建），每张卡单独确认。
- **界面复用**：把 `ChatView` 拆成通用的对话（消息列表、输入框）和网站的外壳；内容管理的面板用通用部分，不带改动审核、素材上传和参考图。
- **技能**：内容管理的会话用一份单独的系统提示，说明工具、确认规则和 Notion 支持的正文范围；不加载网站和主题的技能。

### 分层（约 6–9 天）

- **A0 会话归属**：会话可以属于一个 Notion 数据库（新的归属列和迁移，`ProjectKey` 加 `content/<sourceId>/<databaseId>`）；内容会话的服务（不加锁、不建改动集、只有自定义工具、单独的系统提示）；会话接口挂在数据库路径下。删除数据源时一起删掉它的会话。
- **A1 读取工具**：`read_entry`、`read_schema`、`search_entries`，复用 `NotionContentService`；每条消息带上当前条目 id。
- **A2 提议和写入**：`propose_update`、`propose_create` 的校验和记录；确认、拒绝的接口，写入复用保存和新建（含冲突检查），结果回传给对话。
- **A3 界面**：拆出通用对话组件；中栏底部可折叠面板（会话列表、新对话、消息、输入框）；确认卡（属性对比、正文差异、写入/不要）；写入后刷新列表和条目；窄屏布局。
- **A4 收尾**：开发方案 5.6 和第 14 节、README、AGENTS.md；e2e（用假模型）覆盖读取、提议、确认写入、拒绝、冲突；三种浏览器完整 e2e。

### A0 实现说明（2026-11-22）

- **存储**：迁移 016 重建 `sessions`，加 `data_source_id`（外键到 `data_sources`，删除时级联）和 `database_id`，三种归属正好一种。`SessionStore` 按键选列。
- **服务**：`AgentService` 加可选的 `content`（`ContentAgent`，实现是 `NotionContentAgent`）。内容键的会话：不加网站锁、不建改动集、不等 Bukit、不快照；工作目录是应用临时目录下的空目录 `content-ai`；不加载技能；系统提示是内容助手的；Pi 的工具只有 `ContentAgent.tools` 给的（A0 还是空的）；不收图片。没有 `content` 时内容键一律 404。

- **测试**：`agent.test.ts` 覆盖内容会话的运行（系统提示、没有技能和工具、不占锁）、不收图片、分叉留在同一数据库、随数据源删除、没有 `content` 时 404；`sessions-api.test.ts` 覆盖内容路径下的创建和列表。

### A1 实现说明（2026-11-22）

- **工具**（`agent/content-tools.ts`）：`read_schema`（标题、字段、是否可编辑、选项）、`search_entries`（按标题搜索、按属性排序、翻页，每页 50 条：id、标题、编辑时间、各属性的文字）、`read_entry`（属性和正文；正文用 Markdown 方言，正文只读时 `body` 为空、`bodyReadOnly` 写原因）。都只读这个数据库：读页面和正文时服务端检查页面的父数据库。结果超过 60,000 字符截断并说明。出错时给模型看的是英文说明（例如没有打开的条目）。
- **当前条目**：发消息的请求可以带 `entryId`（只对内容会话有用，格式不对 400）；服务端按会话记下，`read_entry` 不带 id 时读它。不写进对话文字，所以对话里不会多出提示；系统提示要求 AI 处理"这个条目"前先读一次。
- **共用 Notion 服务**：`NotionContentService` 在 `main.ts` 只建一个，内容管理的接口和 AI 工具共用，按数据源排队、每秒不超过 3 次的限制对两边一起生效。
- **已知取舍**：正文有不支持的块时 AI 读不到正文文字，只知道原因。
- **测试**：`content-tools.test.ts` 用假的内容服务覆盖三个工具、按 id 读别的条目、没有打开的条目、只读正文、截断；`agent.test.ts` 确认内容会话里有这三个工具、没有文件工具，`entryId` 格式不对时拒绝。

### A2 实现说明（2026-11-22）

- **提议工具**（`agent/content-proposals.ts`）：`propose_update` 只改当前条目，`propose_create` 新建。属性按名字给简单的值（字符串、数字、布尔、选项名、选项名数组、日期或 `{start, end}`、null），按字段类型换成 `ContentValue` 再用同一个 zod 校验；状态只能用已有的选项（Notion 不会新建状态），单选可以新建。没变的属性不算进提议，什么都没变时拒绝。正文用 Markdown 方言，按保存的规则检查（Notion 不收的内容、长度、块数）；已有的 Notion 图片用 `notion-image:<id>` 保留，只能是这个条目的、每张一次、按原来的顺序（它们在 Notion 里不动），新条目不能带。不合规时把英文说明返回给模型让它改。
- **提议存在哪**：工具结果的 `details.proposal`（类型 `ContentProposal`：条目、标题、读取时的编辑时间、每个属性的旧显示值和新值、正文前后的 Markdown 和要写的块），随会话记录保存，刷新后还在。工具只返回"已记下，等用户决定"，不写 Notion。和原设计的差别：AI 这一轮可以继续回复（例如说明提议），只是不能自己写。
- **决定**：迁移 017 的 `content_proposals` 按（数据源、数据库、工具调用 id）记下写入、拒绝或失败，分叉出去的对话共用同一份决定，同一提议不会写两次。写入成功和拒绝是最终的；失败的可以再试，但正文写了、属性没写（`content.proposal_partial`）的不再试（再试只会冲突）。正在写的提议再点写入或拒绝返回 `content.proposal_busy`。
- **写入**：先按读取时的编辑时间保存正文（`saveBody`，含冲突检查），再用保存后的新编辑时间写属性（`update`）；新条目用 `create`。从会话记录取回的提议写之前再按请求的规则校验一次。Notion 或检查报的错记成失败并返回状态（HTTP 200），卡片显示原因；其他错误也记成失败，同时请求失败并记日志。
- **接口**：`GET /api/sessions/:id/proposals`（这个对话里每份提议的状态）、`POST /api/sessions/:id/proposals/:callId/apply`、`.../reject`。只对内容会话，别的会话 404；对话里没有这份提议时 `content.proposal_not_found`。
- **告诉 AI**：这个对话里做的决定，在它下一次运行开始时作为隐藏消息（`display: false`，对话里不显示）发给模型，发出后标记已告知，只说一次。

### PR #19 评审意见（2026-11-22，Codex 5 条，已修）

- **数据库 id 带短横线时面板 404**：侧栏用 Notion 返回的 id（可能带短横线）做路由，面板拿它拼内容键，`parseContentKey` 不认，会话接口走错路径。面板先把 id 规范成 32 位小写十六进制（`canonicalNotionId`），和服务端一致。
- **页面 id 带短横线时确认卡看不到草稿、写入后不刷新**：提议里的条目 id 没有短横线，编辑器的草稿和查询按路由里的 id。确认卡按规范化的 id 和打开的页面比较，再用路由里的 id 找草稿；写入后刷新这个数据源的条目列表、属性和正文（只有正在显示的会重新读取）。
- **后续消息改了正在运行那一轮的条目**：打开的条目改为跟着消息走：排队和合并的消息在开始处理时才设为当前条目（合并时用最新一条的）；内容会话的"运行后发送"不再交给 Pi 的 follow-up，而是等这一轮结束后作为下一次提问；"插话"进入正在运行的一轮，条目也随之切换。
- **提议用的是读取之后的新版本**：`propose_update` 必须带上 `read_entry` 返回的 `lastEditedTime`，和条目现在的编辑时间不一致就拒绝，让 AI 重新读取再提议，不会用旧内容覆盖期间的修改。
- **长文字属性给 AI 的是截短的显示文字**：`read_entry` 对可编辑属性返回完整的值（和提议工具收的格式一样），只读属性仍是显示文字；确认卡的旧值也用完整的值。

- **（第二次评审）离开条目后草稿不再拦住写入**：草稿离开页面后还在，直到保存、放弃或编辑别的条目。确认卡改为直接看这个条目有没有草稿（`useEntryDirty`，短横线和不带短横线的 id 都认），不管它现在是否打开。
- **（第二次评审）运行中做的决定没告诉后续消息**：决定的说明改在每次提问前收集，一轮运行里排队的后续消息也能先听到用户刚才的决定（包括新建条目的 id）。

- **（第三次评审）新建或正文只写了一部分时还能重试**：`content.body_partial`（新页面的正文没写完且没能移进回收站，或正文替换到一半）和 `content.proposal_partial` 一样算最终结果，不再给重试按钮，免得重复建页。规则放在共享的 `proposalOpen`，服务端和确认卡一致。

### PR #18 评审意见（2026-11-22，Codex 3 条，已修）

- **合并后的长文字存不回**：Notion 一块最多 100 段、每段 2000 字，读回来合成一段可达 200,000 字，原来每段上限 199,900，能编辑的正文保存时被拒。正文的文字段和代码块改用 `CONTENT_SPAN_MAX`（100 × 2000），真正写不进的仍由服务端按 100 段检查拒绝。
- **签名图片地址过期不更新**：重新读到的正文里 Notion 图片的地址变了时重新装载编辑器（有草稿时从草稿装载，不丢内容），不再因为比较时忽略地址而一直显示过期的图片。
- **不能保存时编辑器重新装载会丢内容**：有问题（例如嵌套）时，草稿同时保存编辑器的原始文档和图片信息，窄屏切换、锁定再解锁让编辑器重新装载时从这份文档恢复，问题提示也保留。
- **http 外链图片显示不出来**（第二次评审）：正文接受 http 和 https 的外链图片，CSP 原来只放行 https，http 图片能保存却显示不出来。`img-src` 加上 `http:`，取舍和 https 一样（图片网站能看到请求，不带 referrer）。
